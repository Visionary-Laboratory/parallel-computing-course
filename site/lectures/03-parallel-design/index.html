实际问题：求金属板的稳态温度

一块均匀的薄金属板，左边持续保持 100°C，其余三边保持 0°C，没有内部热源，忽略板面散热。我们想知道：最终稳定下来后，板内各处是多少度？

把板划成等间距网格。稳态时，每个内点流入和流出的热量平衡，因此它的温度等于四个邻居的平均值：

Ti,j=Ti−1,j+Ti+1,j+Ti,j−1+Ti,j+14.T_{i,j}=\frac{T_{i-1,j}+T_{i+1,j}+T_{i,j-1}+T_{i,j+1}}{4}.Ti,j​=4Ti−1,j​+Ti+1,j​+Ti,j−1​+Ti,j+1​​.

Ti,jT_{i,j}Ti,j​ 表示第 i 行、第 j 列的温度。邻居也未知，不能只代入一次就算完；可以先把内部都猜成 0°C，再反复用邻居改进估计。图中 6×6 包含固定外圈，只有内部 4×4 需要求解。

中心与四邻构成五点模板（five-point stencil）；更新时读四邻、写中心。这里的轮数是求解迭代次数，不是现实经过的秒数。

同一块金属板，三种读值规则

从内部全为 0°C 开始，观察 C=(2,1)：它左边是固定的 100°C 边界，上、下、右邻初始都为 0°C。先区分计算时读哪一版数据，以及哪些点安排在一起执行。

算法与执行安排第一轮 C=(2,1) 读到什么C 的新估计
雅可比（Jacobi）：所有点只读上一轮左 100；上、下、右都是 025°C
高斯–赛德尔：逐行执行左 100；上已变成 25，下、右还是 031.25°C
高斯–赛德尔：波前并行与逐行相同：左 100、上 25、下 0、右 031.25°C
高斯–赛德尔：红黑两色左 100；上、下都已变成 25，右仍是 037.5°C

高斯–赛德尔迭代（Gauss–Seidel）会利用已经更新的邻点值。这里的逐行和波前遵守相同的“上、左新；下、右旧”规则：逐行一个点接一个点做，波前把互不依赖的点放在同一批。两者每一轮结果相同，波前是它的并行执行安排。

红黑高斯–赛德尔则改变更新顺序：第一色 i+j 为偶数，第二色为奇数；同色内并行，第一色全部完成后，才开始第二色。因此它每轮的中间结果可以不同。

这些数都是当前估计，不是三个不同的物理答案。切到 100 轮，C 都接近 59.47°C。在这个固定边界的模型中，它们趋向同一个离散稳态，但沿途的估计与所需轮数可以不同。

双缓冲：一份只读，一份写入

要实现雅可比迭代，用两块不同的存储：old 保存上一轮的温度估计，next 接收本轮。每个任务只拥有一个输出点。

text
对每个内点 (i,j)，并行执行：
    next[i,j] = (old[i-1,j] + old[i+1,j]
                 + old[i,j-1] + old[i,j+1]) / 4
等待本轮所有点完成
交换 old 与 next 的角色，进入下一轮

多个任务可以共同读取 old，却不会写到同一个 next[i,j]。左边的 100°C 和其余三边的 0°C，在两块缓冲里都要预先设好，并始终不更新。

快 worker 仍不能独自进入下一轮：它要读取的邻居输出可能还没写完。交换角色只交换引用，不需要把整张网格复制一遍。

写不同格子，就一定能并行吗？

仍看这块金属板，但先只让两个相邻任务工作：A 更新 (1,1)，B 更新右边的 (1,2)。边界不变，其余内点暂时保持初始的 0°C。

A 从左边界得到 25°C。如果 B 随后读取 A 的新值，就得到 6.25°C；如果 B 先读取 A 的旧值 0，就得到 0°C。虽然写不同格子，执行顺序仍会影响结果。

两个任务都只读可以共享同一份旧估计
两个任务都要写需要唯一写者，或明确的同步与合并

波前：沿斜线分批更新温度

回到完整金属板。逐行高斯–赛德尔迭代让 C=(2,1) 第一轮得到 31.25°C。如果要保留每一轮的结果，能否把逐点串行改成并行？

点 (i,j) 需要上、左的新估计，以及下、右的旧估计。按 i+j 从小到大分批：

  1. 上、左在更早的批次，已经写好。
  2. 下、右在更晚的批次，还没覆盖旧值。
  3. 同批点互不读取对方，可以一起更新；一批完成，再推进下一批。

例如 (1,2) 和 (2,1) 都只需等待 (1,1) 算完，就能同时做。这样的推进方式叫波前（wavefront）：它是这里高斯–赛德尔迭代的并行执行安排，改变执行日程，保留逐行求解器的读值版本。

红黑：换个顺序求同一个稳态

波前保留逐行算法，每轮仍有 7 批。可是温度问题真正要求的是最终满足热量平衡，不必每一轮都与逐行算法完全一样。

将内点按棋盘分组：第一色 i+j 为偶数，第二色为奇数。四邻一定异色，所以同色内点可以一起更新；固定边界始终可读。

第一色全部算完 → 同步 → 第二色全部算完 → 同步 → 下一轮。 先偶数色是本例约定，交换两色顺序会影响中间估计。

波前高斯–赛德尔红黑高斯–赛德尔
上、左读新值；下、右读旧值第一色读第二色旧值；第二色读第一色新值
一轮 7 批，最宽一批 4 点一轮 2 批，每批 8 点
与逐行每轮结果一致每轮结果可以不同，但本例收敛到同一个稳态

潜在优势：每批工作更多，需要依次交接的阶段更少。 对 n×n 个内点，波前要推进 2n−1 批，红黑只有两色、每色约一半网格，更容易同时给很多线程分配工作。

仍用 4×4 内点和 4 个同速 worker，假设每点耗时 1、忽略开销：波前需 7 个时间单位；红黑每色 8 点，各分两批执行，两色共 4 个时间单位。两色并不意味着任何资源条件下都只用 2 个时间单位。

实际用途就在稳态导热这类网格方程的求解中。 数值计算库 hypre 的一个多重网格求解器就提供红黑高斯–赛德尔作为可选更新步骤。多重网格让粗、细网格配合修正误差，红黑更新是其中一个部件。

真正更快还要同时考虑每轮计算、同步与访存的成本，以及达到同一精度的轮数；并行机会更多，并不保证完整求解更快。

同步工具：分别保护什么

上一页把频繁共享写入改成了“先算局部结果，再合并”。剩下的协调有两类：多人共同修改时，怎样不冲突？读取别人结果时，怎样完成交接？

工具保护的对象直观例子
原子读改写（atomic read-modify-write，如原子加）一次不可分割的更新多人给同一个计数器加一，不丢增量
互斥锁（mutex）一段需要互斥执行的操作修改一条任务记录的多个字段，避免别人同时修改
屏障（barrier）一组参与者之间的阶段交接大家都写完本轮网格，才能开始使用完整结果

例如，两人都读到计数器为 0，再各自写回 1，最终只增加了 1。“读取是原子的、写入是原子的”不代表整个加一过程不可分割；需要保护的是读取、修改、写回这一整次更新。

屏障只能协调阶段，不能补救阶段内部已经发生的竞争。 先让输出尽量由唯一写者负责，再根据剩下的协调需求选择工具；即使没有多人写同一处，结果交接仍然需要同步。

同步不仅防止冲突，还负责交接结果

接着看上一页的第二类需求。一个 worker 计算局部和，写入自己的 result；主线程负责收集结果。这里只有一个写者，但主线程仍不能想读就读。

交接必须保证两件事：对方已经写完；这些写入对接收者可见。 “可见”指同步关系保证接收者随后能正确读取已交付的结果，不只是从时间上猜测对方已经做完。

成功的 join 不只是等待：它还建立线程结束前的写入与接收者后续读取之间的同步关系。这种有保证的先后关系称为先行发生关系（happens-before）。

睡 1 秒再读不能代替交接：对方可能没做完，而且等待时长本身不建立同步关系。若 worker 不结束，而是还要继续下一轮计算，就需要像屏障这样的阶段交接。

共享地址空间，也有“数据远近”

前面让分区显式交换温度，很容易看见数据在搬。现在把同一块金属板放进多插槽服务器的共享内存，线程能直接读邻区的数组，不用自己发消息，是否就没有数据远近之分了？

非均匀内存访问（NUMA，Non-Uniform Memory Access）：多个处理器共享地址空间，但访问本地内存与另一个处理器附近的内存，路径和代价不同。

例如，某个分区的温度数组位于处理器 A 附近的内存，却让处理器 B 上的核更新它：任务虽然分过去了，读取数组仍要经过处理器之间的互连。共享的是地址空间，访问路径并没有变成一样。

这也回扣前面的任务窃取：空闲核接手远处工作，可能省下排队，却增加远端访存。可以优先安排靠近数据的工作，必要时再跨域平衡负载；是否划算仍要比较总时间。

Top-2：一个 token 去两处，回来后如何合并

前面每个 token 只选一个专家，称为 Top-1 路由。若模型要求一项输入交给两个专家，就增加了结果合并的问题。

Top-2 路由表示每个 token 选两个专家；T 个 token 因而产生 2T 条记录。每条记录用 (token_id, route_id) 标识。

为什么还需要权重？ 两个专家会各自产生一份结果，模型需要决定这两份结果分别乘多大的系数，再把它们相加；这个系数就是此处的路由权重。

权重从哪里来？ 模型中的路由器（router，也称门控模块）根据当前token的特征给专家打分，路由规则据此选择专家并计算合并权重。本页把这些选择和权重作为已知输入，只负责正确搬运和合并。

假设token 5选中专家0和专家2，并采用归一化后的权重0.7、0.3：表示两位专家的输出分别乘0.7、0.3，不是把token的计算量拆成70%和30%；两个专家都处理这份输入。这是本例的权重约定，不要求所有MoE实现都按相同方式归一化。

把专家编号、权重和路由记录对应保存：

text
(token 5, 路由 0, 权重 0.7) → 专家 0 → 临时结果 u
(token 5, 路由 1, 权重 0.3) → 专家 2 → 临时结果 v
一个最终拥有者读取两份结果：out[5] = 0.7 u + 0.3 v

例如某个分量上 u=10、v=20，合并结果就是 0.7×10+0.3×20=13。

分组时给每条记录分配唯一槽位；专家计算完成后，每个 token 的拥有者 gather 两份结果再加权合并，避免两个专家同时对最终输出做普通累加。

这里 u、v 都是同形状向量，公式对每个分量成立。把两份结果分别乘权重，再相加为一份输出，就是一次加权归约（weighted reduction）；不是scan，因为这里不需要每个前缀的结果。两条路由的位置映射必须与权重对应。

当时只算出了答案，没有解释多个执行者怎样同时更新计数表。这里补上这个实现问题：所有token一起计数，会不会争着修改同一个位置？ 继续用每个token只选一个专家的例子。

若共用 count=[0,0,0]，token 0、2、5都要给 count[2] 加1。原子加可以防止漏计，但这些更新仍需协调。大量线程集中修改同一位置，这个位置就叫热点；相互争用叫热点争用。 这里与温度无关，也不是说这个8项小例子已经有严重性能问题。

这与前面“先各算部分结果，再归约合并”是同一种方法。应用到计数上，就是分开数，最后合起来：由两个执行者分别顺序统计前4项和后4项，每人拥有自己的计数表。

执行者A0、1、2、3[2,0,2,1][1,1,2]

两人都完成后，按列相加——[2,3,3]

A、B更新不同的表，统计期间不争同一计数器。这叫私有化：本例是每个执行者各一份；如果多个线程共用一份“组内表”，组内更新仍需同步。

代价也很具体：从3个计数器变成6个，要初始化两份表，再做3次加法合并。一般有P份表、B个桶、每个计数器4 B时，局部表共占 4PB字节。减少争用是否值得，要看省下的等待能否抵过这些新增成本。
