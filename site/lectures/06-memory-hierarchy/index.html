复习：从代码看数据的访问范围

先看同一个 block 中两个线程交换数据。这里用 <<<1, 2>>> 启动，设备数组 a 的前两个数是 10、20：

cpp
__global__ void swap_pair(const float* a, float* b) {
    int t = threadIdx.x;
    float mine = a[t];
    __shared__ float tile[2];
    tile[t] = mine;
    __syncthreads();
    b[t] = tile[1 - t];
}
代码中的数据线程 0 与线程 1 怎样使用
mine线程私有，通常保存在寄存器；两份值分别为 10、20
tile同一个 block 共用一份；同步后可读对方写的位置
a、b 指向的 global 数组Host 事先分配；kernel 结束后仍保留，b 得到 20、10

Shared memory 与 L2 缓存的区别

Shared memory 不是 L2。 两者都在 GPU 芯片内，但位置和使用方式不同：

比较Shared memoryL2 缓存
在哪里各个 SM 内可由多个 SM 访问的缓存层
谁管理数据程序安排装入、使用和同步硬件自动缓存、替换数据
本讲如何使用每个 block 合作使用自己的 tile读取 global 数据时可能命中
cpp
__shared__ float tile[32];
tile[t] = a[i];  // a 指向 global 数组，tile 是 shared 数组

先读取 a[i]：数据可能由 L1 / L2 提供，缓存未命中时才需继续到显存取数；然后写入 shared 中的 tile[t]，供 block 内线程复用。

复用 shared 减少的是重复的 global 读取请求。 Global 是地址空间，不等于每次都访问显存，因此请求减少也不等于显存流量同比减少。

RTX 5090 Laptop 采用这种结构：划给 shared 的容量增大，可用于 L1 的部分减少。色条不代表实际比例。

07 · 主题链接

已有缓存时，Shared memory 的作用

L1、L2 已经能减少显存访问。Shared 的价值在于让程序明确安排：保留哪些数据、由哪些线程共用、按什么顺序交接。

接下来的例子Shared 带来的具体作用
转置：行变成列先由一组线程连续读入，再换分工连续写出；缓存本身不会改变线程的读写分工
GEMM：输入复用合作装入一块输入，供多个输出计算使用；保留到这一轮结束，避免提前被缓存替换
Stencil：相邻输出的邻居重叠合作装入重叠区域，让多个线程共用；若 L1/L2 已有效复用，额外搬运和同步可能不划算

典型过程是：合作装入 → 同步 → 使用 shared 中的数据；覆盖它之前，还要确认其他线程已用完。

Shared 并不保证比 L1 命中更快。是否值得使用，要比较节省的访存与新增的搬运、同步开销；后面用三个实验观察。

连续访问：32 个线程读取相邻元素

看一个 warp 执行 value = a[lane]：lane 为 0…31，每个线程读一个 4 B 的 float。

把地址按 32 B 一格划分，每格能放 8 个 float；这种小段称为 sector。假设 a 的起始地址按 32 B 对齐：

线程读取地址落在哪一格
a[0]…a[7]第 0 格：字节 0…31
a[8]…a[15]第 1 格：字节 32…63
a[16]…a[23]第 2 格：字节 64…95
a[24]…a[31]第 3 格：字节 96…127

32 个线程的请求只覆盖 4 格，整格都用上了。 这就是合并访存容易高效的情形；4 格描述地址覆盖，不等于显存一定发生 4 次传输。

跨行访问：每个线程连续，warp 却分散

假设矩阵每行 32 个 float，线程 lane 读取第 lane 行中的第 k 列：

cpp
value = a[lane * 32 + k];
同一轮读取线程 0线程 1线程 2线程 3
k=0a[0]a[32]a[64]a[96]
k=1a[1]a[33]a[65]a[97]

竖着看，线程 0 依次读 a[0]、a[1]，确实连续。横着看 k=0，相邻线程却相隔 128 B；完整 warp 的 32 个请求落在 32 个 sector 中。

所以判断合并访存，要看同一轮中相邻线程的地址。下一节的转置，恰好会遇到这种跨行访问。

矩阵转置：从 2×3 到 3×2

转置就是行变成列，列变成行，元素的值不变：

A=[123456]⟶B=[142536].A=\begin{bmatrix}1&2&3\\4&5&6\end{bmatrix} \quad\longrightarrow\quad B=\begin{bmatrix}1&4\\2&5\\3&6\end{bmatrix}.A=[14​25​36​]⟶B=​123​456​​.

按行存入内存时，A 排成 1、2、3、4、5、6，B 排成 1、4、2、5、3、6。

让相邻线程分别搬 1、2、3它们访问的位置（从 0 编号）
从 A 读取位置 0、1、2，连续
向 B 写入位置 0、2、4，间隔着写

共享内存的思路：先连续读入一个小块 → 等大家装好 → 换人连续写出。例如读入数字 4 的线程，可以把它交给另一个线程，与数字 1 一起写成 B 的第一行。

朴素矩阵转置：一个线程搬一个元素

把刚才的 2×3 推广为 M×N：A 为 M×N，B 为 N×M，均按行存储；目标是 B[x,y] = A[y,x]。先看 06_transpose.cu 的朴素 kernel：

cpp
__global__ void naive(const float* a, float* b, int m, int n) {
    int x = blockIdx.x * 32 + threadIdx.x; // A 的列
    int y = blockIdx.y * 32 + threadIdx.y; // A 的行
    if (x < n && y < m)
        b[size_t(x) * m + y] = a[size_t(y) * n + x];
}
// Host：每块 32×32 个线程，每线程处理一个元素
dim3 block(32, 32), grid((N + 31) / 32, (M + 31) / 32);
naive<<<grid, block>>>(d_a, d_b, M, N);

同一 warp 的 x 连续：读 A 时相邻线程取相邻元素；写 B 时相邻线程跳到不同的行，相隔 M 个 float。

size_t(y) * n + x 就是“行号 × 每行元素数 + 列号”；size_t 让乘法使用较宽的索引类型。

共享内存转置：完整 kernel

仍用 32×32 个线程，每线程装一个、写一个。先完整看 shared32 的核心：

cpp
__global__ void shared32(const float* a, float* b, int m, int n) {
    __shared__ float tile[32][32];
    int tx = threadIdx.x, ty = threadIdx.y;
    int x = blockIdx.x * 32 + tx;
    int y = blockIdx.y * 32 + ty;
    if (x < n && y < m) tile[ty][tx] = a[size_t(y) * n + x];
    __syncthreads();
    int out_x = blockIdx.y * 32 + tx;
    int out_y = blockIdx.x * 32 + ty;
    if (out_x < m && out_y < n)
        b[size_t(out_y) * m + out_x] = tile[tx][ty];
}

先按行装入 → 全块同步 → 换人按行写出。源码用 tiled<32> 表示这个版本；<32> 是选定数组行跨度的 C++ 模板参数。改成 tiled<33> 只把 shared 每行长度改为 33，线程数不变。

14 · 主题链接

转置数据写回：两处坐标交换

cpp
int out_x = blockIdx.y * 32 + tx; // B 的列：来自 A 的行块
int out_y = blockIdx.x * 32 + ty; // B 的行：来自 A 的列块
if (out_x < m && out_y < n)
    b[size_t(out_y) * m + out_x] = tile[tx][ty];

交换 block 坐标，把整块放到 B 的正确位置；交换 tile 下标，把块内的行变成列。相邻 tx 仍向 B 的连续列写入。

例如 A[1,4]：线程 (tx=4,ty=1) 装入 tile[1][4]，线程 (tx=1,ty=4) 将它写到 B[4,1]。

块内同步与数据可见性

转置的 barrier 位于合作写 shared与从其他线程写的位置读取之间。它同时提供 block 内的会合与相关内存可见性保证。

cpp
// 正确结构：谓词只包围有效读写
if (valid_input) tile[...] = a[...];
__syncthreads();
if (valid_output) b[...] = tile[...];

不要把整个结构放入随线程变化的 if (valid)，再让部分参与者跳过同步。设计协作时应明确所有需要的数据由谁提供。

Shared memory 的 32 个 bank

Shared memory 内部分成 32 个可以并行服务的存储分组，称为 bank。一个 bank 可以放很多个数。

看一个从 bank 0 开始的 float s[]：每个 float 占 4 B，相邻元素依次分给相邻 bank，分完 32 个再从头开始。

Bank 0Bank 1Bank 2Bank 3…Bank 31
s[0]s[1]s[2]s[3]…s[31]
s[32]s[33]s[34]s[35]…s[63]
s[64]s[65]s[66]s[67]…s[95]

因此，本例 bank 编号 = 元素下标除以 32 的余数。例如 s[0]、s[32] 在同一个 bank，但它们是两个不同位置。

判断冲突，要看同一 warp 的同一条 shared 访问指令：不同线程的请求落到哪些 bank？请求的是不是同一个位置？

同一个 bank、不同位置 → 分开服务；同一个位置 → 读取一次，广播给多个线程。 广播讨论的是读操作。

转置中的 padding：为什么 32 改成 33

转置写回时，同一 warp 的线程沿 shared 的一列读取 tile[tx][0]。先列出线程 0、1、2、3 的地址：

每行占多少个 float元素偏移：行号 × 每行跨度Bank：偏移除以 32 的余数
320、32、64、960、0、0、0：不同位置挤在同一 bank
330、33、66、990、1、2、3：分到不同 bank

改为 __shared__ float tile[32][33];，只是给每行末尾空出一个位置，让下一行起点错开一个 bank。

完整的 32 个线程也遵循这个规律：跨度 32 时产生 32 路冲突；跨度 33 时分别使用 bank 0…31，没有冲突。

有效数据仍是 32×32，每个 block 多用 32×4 = 128 B。线程数、计算结果和 global 数组的布局都不变。

朴素 GEMM 中的重复读取

把刚才的 2×2 推广为 C[M,N] = A[M,K] B[K,N]。先保持每线程一个输出，看看朴素代码怎样重复读取输入：

cpp
// 06_gemm.cu：block(16,16)，每线程一个 C[row,col]
int row = blockIdx.y * 16 + threadIdx.y;
int col = blockIdx.x * 16 + threadIdx.x;
if (row < M && col < N) {
    float acc = 0;
    for (int k = 0; k < K; ++k)
        acc = fmaf(A[size_t(row)*K+k], B[size_t(k)*N+col], acc);
    C[size_t(row)*N+col] = acc;
}

fmaf(a,b,acc) 是 FP32 乘加。相邻输出反复需要相同 A、B 输入；本讲把第一讲的分块复用写成 CUDA，使用普通计算核心。

GEMM 输出分块与输入复用

输出 C[row,col] 在某个 k 上需要 A[row,k] 和 B[k,col]。

同一 block 内需要同一个值的线程
同一输出行的 16 个列位置都需要 A[row,k]
同一输出列的 16 个行位置都需要 B[k,col]

沿 K 一次取 16 项：先合作装入 16×16 个 A + 16×16 个 B，然后计算这一段对 256 个输出的贡献。

输入块在 shared 中共用；每个线程自己的 acc 保留部分和。处理完本段，再装下一段 K。

GEMM 输入加载与越界补零

cpp
constexpr int T = 16;
__shared__ float As[T][T], Bs[T][T];
int tx = threadIdx.x, ty = threadIdx.y;
int row = blockIdx.y*T + ty, col = blockIdx.x*T + tx;
float acc = 0.0f;
for (int base = 0; base < K; base += T) {
    As[ty][tx] = (row<M && base+tx<K)
        ? A[size_t(row)*K + base+tx] : 0.0f;
    Bs[ty][tx] = (base+ty<K && col<N)
        ? B[size_t(base+ty)*N + col] : 0.0f;
    __syncthreads();
    // 下一页：计算与再次同步
}

M、N、K 不要求是 16 的倍数。边缘线程仍参与搬运与同步，无效位置补 0，最后仅写合法输出。

GEMM 尾部处理：K=18 的示例

每个输出的点积需要 k=0…17，K 方向共两轮：第一轮覆盖 0…15，第二轮覆盖 16…31。

Stencil：相邻输出共享哪些输入

设输入 x = [1, 2, 3, 4, 5, 6, 7]，下标从 0 开始。每个输出取“自己与左右各两个邻居”的平均值：

输出需要的 5 个输入值平均值
y[2]1、2、3、4、515 ÷ 5 = 3
y[3]2、3、4、5、620 ÷ 5 = 4

两个线程共用了 2、3、4、5 这四个数；分别读取要发出 10 次请求，但实际只涉及 6 个不同的输入。

共享内存的思路：把共同需要的一段输入装好 → 同步 → 每个线程取自己的 5 个数求平均。

推广到更长的数组：若一组线程负责中间连续 8 个输出，就需要 左侧 2 个 + 中间 8 个 + 右侧 2 个 = 12 个输入。两侧额外的邻居区域称为 halo。

一维 Stencil：半径为 2 的邻域平均

把刚才的邻域平均写成一般形式：输入 x 长度为 N，输出 y 长度相同。数组边缘缺少的邻居视为 0，分母仍为 5；x、y 不重叠。

yi=xi−2+xi−1+xi+xi+1+xi+25.y_i=\frac{x_{i-2}+x_{i-1}+x_i+x_{i+1}+x_{i+2}}{5}.yi​=5xi−2​+xi−1​+xi​+xi+1​+xi+2​​.

cpp
float sum = 0;
for (int d = -2; d <= 2; ++d) {
    int j = i + d;
    if (j >= 0 && j < n) sum += x[j];
}
y[i] = sum * 0.2f; // 前提 i<n，索引规模在 int 范围内

仍用上一页的 x=[1,2,3,4,5,6,7]，y[0]=(0+0+1+2+3)/5=1.2；边界也除以5。

前面用转置重排访问、用 GEMM 复用输入；现在把两种判断迁移到第三讲的邻域计算。一个输出需要中心及邻居，因此 tile 除了主体还要带 halo。

Stencil 的协作加载与块内同步

cpp
constexpr int B = 256, R = 2;
__shared__ float tile[B + 2*R];
int t = threadIdx.x, base = blockIdx.x * B;
for (int j = t; j < B + 2*R; j += B) {
    int g = base + j - R;
    tile[j] = (g >= 0 && g < n) ? x[g] : 0.0f;
}
__syncthreads();

launch 必须为 B 线程；规模限制确保有符号索引不溢出。前 4 个线程额外装入最后 4 个 shared 位置。

所有线程都参加装入与 barrier，包括最后一块里没有有效输出的线程。无输出不等于无协作职责。

Stencil 输出计算与边界处理

cpp
int i = base + t;
if (i < n) {
    float sum = 0;
    for (int d = 0; d < 5; ++d) sum += tile[t + d];
    y[i] = sum * 0.2f;
}

每个有效线程连续读取 5 个 shared 元素，邻居会复用其中 4 个。kernel 结束后这个 tile 不再复用，所以这里不需要再加一道“准备下一轮覆盖”的 barrier。

Stencil 演示程序包含 naive/shared 两版、N=0/1/3/257/1003 等边界检查和 CPU 参考。它与前面 GEMM 的区别在于，GEMM 会在同一 block 中反复覆盖 shared tile。

CUDA stream 与任务依赖

37 · 主题链接

CUDA stream：任务队列与执行顺序

前面的 shared 解决 一个 kernel 内的数据协作。现在回到第五讲的“上传 → kernel → 下载”，观察 多个任务之间怎样安排顺序。

Stream 是提交 CUDA 操作的有序队列。 同一 stream 中，后面的操作等待前面的操作完成；CPU 可以先把它们依次提交出去。

text
CPU 提交顺序：上传 A，计算 A，下载 A
GPU 队列顺序：[上传 A] → [计算 A] → [下载 A]

以前写 kernel<<<grid, block>>>，用的就是默认 stream，并不是没有 stream。

多个 stream 可以表达互相独立的工作；它们共享 GPU 资源，不保证同时运行，也不各自独占一个 SM。

38 · 主题链接

异步提交：CPU 可以先做独立的工作

cpp
add_one<<<grid, block>>>(d_in, d_out, n);
CUDA_CHECK(cudaGetLastError()); // 检查提交错误，不等待计算结束
prepare_next_input();           // CPU 工作：与当前 GPU 缓冲无关
CUDA_CHECK(cudaDeviceSynchronize());
// 等 GPU 完成后，才继续依赖它的步骤

异步说的是“调用返回时，任务可能还没完成”。 CPU 可以在 GPU 计算时准备下一份输入，不必启动多个 stream 才能做到。

若 CPU 做的是读取本次 GPU 结果，就必须等结果可用。若马上调用同步函数，CPU 仍会在这里等待。

“CPU 没在等”与“两个 GPU kernel 同时执行”是两个问题；后者需要独立 stream 和足够的执行资源。

Pinned 主机内存与异步复制

06_stream.cu 仍计算最简单的 out[i] = in[i] + 1。要让 Host↔Device 传输有机会与其他任务重叠，先准备 pinned 主机内存：

cpp
float *h_in, *h_out;
size_t bytes = size_t(n) * sizeof(float);
CUDA_CHECK(cudaMallocHost(&h_in, bytes));
CUDA_CHECK(cudaMallocHost(&h_out, bytes));
// 初始化输入，提交任务，等待完成；然后释放
CUDA_CHECK(cudaFreeHost(h_in));
CUDA_CHECK(cudaFreeHost(h_out));

Pinned 表示这些 CPU 内存页被固定，便于设备直接传输；它没有把数组变成 GPU 显存。

后面使用 cudaMemcpyAsync(..., s) 指定复制队列。普通 malloc / std::vector 内存可能触发暂存或等待，不能仅凭 Async 名字断定已实现重叠。

同一 stream：上传、计算与下载

06_stream.cu 的计算与提交核心如下；h_in、h_out 为 pinned 内存，设备缓冲已分配：

cpp
__global__ void add_one(const float* x, float* y, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = x[i] + 1.0f;
}
cudaStream_t s;
CUDA_CHECK(cudaStreamCreateWithFlags(&s, cudaStreamNonBlocking));
CUDA_CHECK(cudaMemcpyAsync(d_in, h_in, bytes, cudaMemcpyHostToDevice, s));
add_one<<<(n + 255) / 256, 256, 0, s>>>(d_in, d_out, n);
CUDA_CHECK(cudaGetLastError());
CUDA_CHECK(cudaMemcpyAsync(h_out, d_out, bytes, cudaMemcpyDeviceToHost, s));
CUDA_CHECK(cudaStreamSynchronize(s));
CUDA_CHECK(cudaStreamDestroy(s));

启动配置的第三项 0 是动态 shared 字节数，第四项 s 才是 stream。无需在上传和 kernel 之间插入 CPU 等待；队列已经保证先后，最后同步后 CPU 才能读 h_out。

不同数据块的传输与计算重叠

把数组分为互不重叠的 A、B 两段：每段内部仍是 上传 → 计算 → 下载，但“计算 A”不需要等待“上传 B”。

仅把同一份数据的三个阶段放进三条队列，不能消除它们的依赖。能重叠的是 不同数据段的独立工作。

图表示一种可能的安排；真实重叠还取决于 pinned 内存、复制引擎、计算资源和任务大小。

42 · 主题链接

两条 stream：保持每段数据的依赖

完整源码用 submit_chunk 封装上一页的“上传 → 加 1 → 下载”。它只提交，不在内部等待：

cpp
// n0 + n1 = n，两段数据使用不重叠的缓冲区域
submit_chunk(h_in, h_out, d_in, d_out, n0, s0);
submit_chunk(h_in+n0, h_out+n0, d_in+n0, d_out+n0, n1, s1);
CUDA_CHECK(cudaStreamSynchronize(s0));
CUDA_CHECK(cudaStreamSynchronize(s1));

先提交两段，再等待完成。 若每提交一段就立刻同步，CPU 会等第一段全做完，才有机会提交第二段。

在同步前，不要改写正在上传的 h_in，也不要读取正在下载的 h_out；释放缓冲也要等使用者结束。

比较时，一条 stream 也提交相同的两段，只把两次提交都交给 s0，保持总数据量与任务数相同。

43 · 主题链接

使用 event 建立跨 stream 依赖

如果 s1 必须使用 s0 的结果，CPU 先提交 s0、再提交 s1，并不足以保证 GPU 的完成顺序：

cpp
cudaEvent_t ready;
CUDA_CHECK(cudaEventCreateWithFlags(&ready, cudaEventDisableTiming));
add_one<<<grid, block, 0, s0>>>(d_in, d_tmp, n);
CUDA_CHECK(cudaEventRecord(ready, s0));
CUDA_CHECK(cudaStreamWaitEvent(s1, ready, 0));
add_one<<<grid, block, 0, s1>>>(d_tmp, d_out, n);

ready 是 s0 中的“完成标记”。s1 后面的任务等标记完成后才执行，CPU 不在这个 wait 调用处等结果。 这里连做两次加 1，最终应得到输入加 2。

cudaStreamSynchronize(s1) 则让 CPU 等待 s1 完成；两者等待的一方不同。完整源码在消费完成后销毁 event 并释放缓冲。
